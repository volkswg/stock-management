## Order-bill bigint identity: released

Scope is only `stock_operational.order_bills.id`: preserve every canonical ID while
changing physical storage from text to `bigint GENERATED BY DEFAULT AS IDENTITY`.
The exact existing nonempty-text ID CHECK becomes `id >= 0`; its inverse restores
the original CHECK. Other business IDs, incoming relationships, API fields and LINE
flows stay unchanged.
The app returns IDs as strings, including values beyond JavaScript number precision.
Creation sorting stays `createdAt`, unknown dates last, with the existing text/C ID
tie-break. A sequence permits gaps after rolled-back reservations; IDs are not a
count or gapless business number. Direct Supabase inserts should omit `id`; manually
supplying a new ID can collide with the sequence and is outside this procedure.

Release order requires separate owner approval:

1. Merge/review CI, verify fresh private recovery covering all53 tables, configuration
   credentials, grants and metadata; restore independently on a disposable local
   database. After conversion, recovery must also capture and restore the new
   sequence's value and `is_called`, including gaps from rolled-back reservations.
   The existing backup reader receives SELECT on this sequence only.
2. Deploy the corrected dual-layout app, including the shared edit-revision text
   projection, first on the unchanged text schema. Compare browser
   and LINE read behavior, then retain the exact compatible build as rollback.
   The initial PR90 app (`f7f50b2`) and older builds **cannot run after the bigint
   conversion**: its edit-revision UNION still mixes text and numeric IDs. Never
   promote a build preceding this correction against the bigint schema.
3. Obtain a supervised maintenance window, drain browser/LINE/direct-editor/job
   writes, fence writes and verify the checkpoint freshness, no late writes, exact
   target `hzynvirpedqnvtbifobx`, isolation
   `349b9289-f684-4ec5-ac22-924b2be1946b`, purpose `production`, and no external
   text-ID consumers. Recheck all IDs including soft-deleted rows: no aliases,
   leading zeros, negatives, non-numeric values or exhausted bigint capacity; no
   incoming FK, dependent view or pre-existing sequence. Stop on any mismatch.
4. The approved owner uses a verified private PGSERVICE and `psql -Xw -v
   ON_ERROR_STOP=1`. Set these session GUCs to the independently verified receipt:
   `stock.allow_bill_identity_conversion=reviewed-order-bill-bigint-v1`,
   `stock.bill_identity_restore_verified=business-and-config-v1`,
   `stock.bill_identity_source` (reviewed full40-character source SHA),
   `stock.bill_identity_fingerprint` (private full64-character recovery hash),
   `stock.bill_identity_revision` (frozen global revision),
   `stock.expected_isolation_id` and `stock.expected_purpose` (exact target above).
   Execute only `tools/migration/operator/20261120022134_order_bill_identity.sql`.
   It is deliberately outside automatic migration discovery. The gates attest the
   operator's verification; setting them is not itself a recovery verification.
5. Compare every record, row/global revision, media reference, permission and

   app and stop for reconciliation; do not restore an old snapshot over new work.

No live SQL, production records, Vercel settings, traffic controls or other table
IDs are changed by preparing this PR. Backup automation stays deferred.

## deletedAt soft-delete consolidation (prepared; production unchanged)

and production reopened**. Do not rerun its operator SQL. The following procedure
is the historical release/inverse contract. The native adapter source change now
requires the final validated `deletedAt`/media-ID schema and refuses older layouts.

it does not cascade children or delete Drive files.

The [operator SQL](../tools/migration/operator/20261119013852_retire_archived_at.sql)

copies an archive instant only when `deletedAt` is NULL, then drops `archived_at`.
Different non-NULL instants are a hard stop requiring an explicit resolution;
neither is silently discarded. Existing soft-deleted rows remain hidden, including
direct Supabase edits. The shared OLD/NEW guard now protects `deletedAt` and keeps
row revisions. Seventeen validated UTC-range CHECKs cover the renamed timestamps.
Active unique-index predicates follow the rename; the shipment-order predicate
becomes the equivalent single deletion check. Public permissions do not expand.
The seven existing append-only runtime tables remain append-only; this change
does not grant the app deletion/edit access to compensation, settlement, adjustment
or receipt-history tables. Authorized direct editors retain their existing rights.

Release requires a separate approval for the exact commit, schema and traffic
controls. Before any live DDL:

1. Verify a fresh private recovery using `--include-media` (all52 tables/15 metadata),
   restore/rehearse locally, then obtain a supervised pause of browser/LINE users,
   direct editors, jobs and scripts with pending work accounted for. Block writes
   and LINE, drain transactions and recheck the complete frozen checkpoint.
2. Capture the **private** pre-change deletion state using
   `python3 tools/migration/soft-delete.py checkpoint-sql` and approved private
   `psql -XqAt` with exact `stock.expected_isolation_id`/`stock.expected_purpose`.
   Save mode0600; never publish its rows. Generate the private inverse with
   `python3 tools/migration/soft-delete.py rollback /private/path/state.jsonl`.
   Rehearse that exact inverse locally before proceeding.
3. Stage and verify the reviewed compatible app, then promote it while traffic is
   blocked. The old schema remains supported. Set exact target/purpose/frozen
   revision, reviewed sourceSHA40 and fingerprintSHA256 in
   `stock.expected_isolation_id`, `stock.expected_purpose`,
   `stock.soft_delete_revision`, `stock.soft_delete_source` and
   `stock.soft_delete_fingerprint`; set
   `stock.soft_delete_restore_verified='52-tables-15-metadata-v1'` and
   `stock.allow_soft_delete_retirement='reviewed-deleted-at-v1'` only after the
   independent restore/freshness checks. These are operator attestations, not a
   substitute for doing the checks. Run the operator file with ON_ERROR_STOP.
4. Verify both schema contracts, all52 normalized table fingerprints, all surviving
   metadata/permissions, exact deletion-state mapping, API reads and LINE signature/
   cutoff/idempotency guards. Verify revisions and original payloads are unchanged.
   Old immutable apps cannot run on the final layout. Remove only this release's

DDL/backfill is atomic, under exclusive locks, with short lock/statement timeouts.
Only the six guarded backfills temporarily suspend their row/global-revision

revision and exact six-table identities, row revisions and expected deletion instants.

## Recovery checkpoint

Backup automation remains deferred by the owner. A verified one-off checkpoint is
still required before destructive/schema maintenance. Keep business records,
credentials, keys, dumps, hashes and reconciliation receipts on the Mac or approved
private storage. Do not publish them in a PR or upload CI production artifacts.

1. Verify the exact target, purpose, read-only TLS profile and complete SELECT/RLS
   coverage. Use the existing approved private service/passfile setup; never paste
   credentials into shell arguments, documentation or chat.
2. Capture all 51 private tables and 15 metadata sections with one consistent
   exported snapshot. Retain the dump, fingerprint and receipt checksums. An archive
   listing/checksum alone is not a verified restore.
3. Restore into a new empty, network-isolated local PostgreSQL target. Reconstruct
   password-free role/membership metadata, locale and necessary dropped-attribute
   gaps so the strict owner/ACL/column fingerprint remains meaningful.
4. Verify every stored table and metadata section. Rehearse the exact approved SQL
   and a schema-only rollback; compare actual application/LINE consumers and local
   create/edit/archive behavior. No live provider or business canary is implied.
5. An online checkpoint may precede subsequent writes. Recheck all tables and
   metadata under the final write fence. Refresh and restore/rehearse if anything
   differs; a matching revision alone is insufficient.

The versioned [recovery tool](../tools/migration/recovery.py) supports `capture`
and `verify`, exact `--target-id` / `--target-purpose production`, one or two
bounded workers and `--row-digests`. A restricted backup reader also needs
`--row-security-reader`. Its ordinary snapshot takes cooperative writer locks;
do not run it on live production while describing it as a non-blocking backup.
Use the separately reviewed online capture packet when users must keep working.
Do not borrow an old wrapper or assume its timeouts and approvals still apply.

The checkpoint covers the private application schemas and password-free recovery
metadata, not managed Supabase Auth/Storage, service passwords, Drive image bytes
or external provider outcomes. Verify independent encryption/decryption and
off-device key recovery when those are part of the approved backup scope. Do not
claim those properties from a successful local database restore.

## Maintenance procedure

Every live schema/deployment/traffic change needs separate explicit approval for
its exact target, source/SQL hashes and effects. Merge, CI and an earlier closed
window are not fresh execution approval. Keep users running during preparation.

1. **Prepare:** verify merged source and passing CI, current schema dependencies,
   live deployment/env/LINE/protection bindings, fresh recovery and local rehearsal.
   Prepare an exact forward/inverse packet; use original migrations as history,
   not instructions to rerun them against the final production schema.
2. **Confirm the window:** name the supervising owner and reopening/abort deadline.
   Confirm browser/LINE users, direct Supabase editors, jobs and scripts are paused,
   with all pending saves/uploads finished or accounted for without uncertain
   provider outcomes. Pause external writers too; do not assume Vercel covers them.
3. **Fence and drain:** publish only the reviewed temporary rule denying methods
   other than GET/HEAD/OPTIONS. Verify browser mutations/LINE are denied, reads are
   available and active/prepared business transactions have drained. Preserve all
   original rules. LINE retries/WAF denial are not a durable event inbox; this
   procedure relies on the confirmed sender pause. Other event-hold arrangements
   need their own verified loss-safe procedure and approval.
4. **Reconcile:** match the complete frozen checkpoint, not only its revision.
   Capture the same four canonical GET baselines: orders, movements, shipments,
   employees. Keep response bodies private and transient; retain hashes, order,
   type and revision evidence. Stop or refresh recovery on drift.
5. **Apply:** execute only the reviewed operator artifact and hash-bound settings.
   Bind isolation/purpose/revision/source/recovery before and after writer/table
   locks; use the artifact's bounded timeouts. Unknown dependencies, role/ACL drift,
   partial schema or insufficient time are abort conditions. Inspect uncertain
   outcomes before retrying. Never silently repair records to pass a gate.
6. **Verify:** require all 51 table values and metadata unchanged except the
   explicitly approved schema delta, preserving owners/ACLs/RLS, journals, IDs,
   revisions and timestamps. Compare the four HTTP responses exactly. Do not
   replace signed-LINE/provider evidence with an unapproved real transaction.
7. **Reopen:** remove only this window's rule. Verify the original firewall,
   deployment/env, LINE cutoff/signature rejection and idempotency guards, plus read
   availability. Scan the actual live deployment's runtime error counts and save
   private receipts. Reopen users/jobs only after the checks pass.

Vercel's firewall version and publication timestamp change when a reviewed rule is
published. Compare them against that exact active configuration; all protection
settings and original rules must remain unchanged. Do not disable a protection to
make a health check pass or create a broad deployment bypass.

## Rollback and refusal conditions

- Before commit, a failed guarded transaction must roll back atomically. Check
  actual schema state and transaction outcome rather than blindly resubmitting.
- After commit and before reopening, keep the fence active. Use only the reviewed,
  locally rehearsed schema-only inverse if its exact forward-state and revision
  gates still hold. Verify records and original metadata before reopening.
- After reopening, newer acknowledged writes must never be overwritten by an old
  dump or a switch back to stale Google Sheets. Stop, inspect journals/provider
  uncertainty and prepare an approved rollback/reconciliation against current data.
- Application rollback needs an exact compatible schema/deployment/config binding.
  Never assume an older build supports removed columns or new writes merely
  because its reads once passed. Current PR80 code supports the PR81 schema change;
  that specific compatibility is not a general permission to roll back releases.
- Keep protected staging, retained imports and unrelated resources untouched. No
  paid resource, account creation, provider action or fresh Sheets synchronization
  is authorized by this document.
